# Social writing / 社交接话

读原帖、相关对话、关系和当前要求，先判断正在发生什么交流。看不到图片或梗时不装懂；已有文字足够就继续。普通感谢或反应不例行研究行业背景。

认可、感谢、共鸣、庆祝、玩笑、补充判断、分歧和提问都可以成立，选贴合这次交流的一种。回复不必是建议或提问，也不固定“赞一句，再问一个问题”；不把同一问题换三种措辞当成三种风格。简单感谢或确认用本参考即可；用户要求比较接话方式，或具体交流难以判断时，才读 [接话方式](reply-moves.md)。

普通回复宜短、口语，像本人在打字：一个主要意思，带一个已有的具体细节。`nice`、`thanks`、`haha` 或 emoji 可以完成交流；emoji 偶尔用，不叠多个。不强迫小写、俏皮话、错字或固定字数。

回复前先看能看到的对话里，用户是否已经就同一点回复过这个人；对这个人不再说一遍。提问前检查对方是否已回答、问题是否有用、关系是否合适。作品分享不例行变成验收，吐槽不例行变成建议，感谢可以自然结束。判断或反驳给关键依据；不为互动硬找分歧，不编造“我也遇到过”。

想邀请别人接话时，可以用一句真实的坦白加一个好答的真问题，或简单的选边、投票；这种写法往往更能让人接话。保持自然，不硬造经历或立场。

英文按自然英语组织，不逐字搬运中文语气词；中文保持合适的口语。短回应可以自然结束，专业解释仍须保留读者需要的条件和依据。

## 先选交付形式，再看要不要分析

按下面的表读取；需要两份时，先读评论，再读帖子成稿，每份只读一次。

| 要交付什么 | 在本文件之外再读 |
|---|---|
| 普通回复、感谢、简单确认 | 无；只在接话方式难判断时读 [接话方式](reply-moves.md) |
| 给原作者的直接回复，需要判断新闻或技术进展的影响 | [新闻与技术进展评论](social-commentary.md)，不读帖子成稿 |
| 原创短帖、引用帖、长帖或 Article | [帖子成稿](social-posts.md)；只有要判断新闻或技术进展时，才先读评论 |
| 为社媒写作做选题或预分析，不交付帖子 | 评论，不读帖子成稿 |
| 工作邮件、正式报告、手册或指定译法 | 按入口走各自路线，不读社交参考 |

个人风格和反馈维护分别按入口条件读 [profile](profile.md) 或 [learning](learning.md)，不因为一条社交回复或帖子就一起加载。外部样本只说明措辞与节奏，父帖未知时不能证明关系和恰当性。

用户要求对照，或本参考不足以判断具体表达边界时，可读 [社交正反例](../examples/social.md)；不默认加载。例子不是固定口头禅，也不提供可冒用的经历。
