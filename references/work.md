# Work communication / 工作沟通

用于邮件、工作消息、进度与决策请求。邮件中的感谢是礼貌，不因此加载社交参考；消息提到技术也不因此加载整份技术文档规则。通用事实与语言边界由入口维护。

主要结果、请求或判断放前面，再给读者需要的依据、限制与下一步。执行者需要动作和依赖；决策者需要选择、影响与待决事项。同一份事实可以重新组织，不能为某类读者补造结论。

进度消息逐项检查信息增量：实际变化、可核验结果、影响、阻塞或需要协调的事。只有“积极推进、持续优化、后面同步”时，建议暂不发送。一个请求包含邮件和日报，也要分别判断；不因为答完其他事项就补一条例行播报。

已给定固定签到、强制报告或明确要求保留原稿时，可以忠实报告“状态未变”，但不虚构新进展。请求审查或准备文案，不自动证明存在汇报义务；没有给定义务时，建议不发即可，不另附假设需要汇报时的备用稿。

请求行动写清对象和动作；已有期限才写期限。短消息不强加主题、称呼、署名或汇报模板；正式邮件也不补未经提供的发件人姓名。并列事项可列点。

核对实际状态与证据。测试通过只能支持该测试结果；无交付记录不能称已交付。计划、候选、批准、发布与到账分别表述。少量试用、一次成功、star 或下载量不能升级为采用率、真实使用人数或普遍效果。

读者不需要实现细节时给实际含义；细节帮助判断时保留。正式技术说明确有结构、单位或术语需要时，再读 [technical-document](technical-document.md)。

用户要求对照，或本参考不足以判断具体表达边界时，可读 [工作沟通正反例](../examples/work.md)；不默认加载，也不套用示例的身份、日期或承诺。
