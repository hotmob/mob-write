# Mob Write 项目宪法

**Write with purpose, for your reader.**

Mob Write 是一个轻量、可安装的写作 skill。它帮助作者决定什么值得写、怎样让读者理解，并产出忠实于事实和意图的文字。它不代替作者的判断，也不自行获得发送或发布权限。

## 我们坚持什么

1. **先判断价值，再处理措辞。** 从目的、读者、关系和场景出发，让文字帮助理解、判断、行动或完成自然的交流。感谢、共情可以成立，无须硬加问题；没有新信息或协作需要的例行播报可以建议省略。明确的报告要求仍需尊重。
2. **忠实于事实、意图和承诺。** 保留数字、条件、否定、不确定性、明确要求原样保留的引文或代码及承诺强度。计划、草稿、测试通过、已交付和已发送是不同状态。缺少证据时限定说法，不补写经历、成效或个性。
3. **读者语言与审阅语言分别判断。** 用中文审稿不代表正文应该发中文。优先使用任务材料和已授权的收件人上下文；影响交付而无法确定的信息才需要询问。
4. **风格服务内容。** 不把“去 AI 味”、一味简短、模仿名人或互动增长当作目的。长度、结构、语气取决于读者需要；保留有用细节，删掉重复、空话和无依据推断。
5. **公共方法与私人声音分开。** Mob Write 是品牌名，不代表默认 Mob 人设；公共默认没有个人身份或私密偏好。个人 profile 可选、局部适用，不能覆盖事实、收件人语言和授权边界。私人样本、反馈、路径与会话不进入公开包。
6. **一个 canonical 源，按需读取。** 根 `SKILL.md` 拥有通用决策与路由，只有 `mob-write` 一个活动入口。场景参考只补充适用内容；教学例按需帮助理解规则，不是默认加载的模板库或第二套规范。生成包可以复制文件，不能成为第二套人工维护规则。检查适用方法是指引，不是运行时强制门禁。
7. **用实际输出与读取证据验收。** 分别验证源版本、包、安装和宿主实际读取，检查遗漏与多读。写作价值需要具体请求和真实产出；打包成功、stars、下载量都不能代替质量或真实使用人数。
8. **有证据地演进，保留退路。** 变化应说明观察到的问题、预期行为和验证结果。保留历史与已知版本；旧入口的破坏性迁移须说明影响并提供可恢复备份，不保留重复活动入口。升级不覆盖未识别或已修改的安装；回退不强行覆盖私人数据。结构检查与模型写作行为分开验证，教学题的复现不能代替留出变体和实际使用。继续保留许可证和来源。

## 范围与迭代

当前服务消息、邮件、社交回复、文章和技术说明，支持中文表达与其他交付语言。只在实际任务需要时扩展场景或工具；不建设知识平台、账号运营系统、后台服务或遥测系统。

每次迭代说明“解决什么问题、对谁有用、怎样验证、如何迁移”。原则变动应在版本记录中说明理由和影响；不因规则更长或功能更多就声称更好。四阶段安排见 [路线图](roadmap.md)，当前实现见 [设计](design.md)。
